# Shared binding specification

`api.yaml` is the small declarative description of the C++ API exposed by the
language wrappers. It is intentionally not a second copy of SymEngine's C++
signatures: every entry names the owning header and validation uses srcML to
verify the selected free-function overload or constant declaration.

Run validation from the super-project root:

```bash
python -m tools.binding_codegen validate
```

The YAML is parsed once into `tools.binding_codegen.model.BindingSpec`; future
renderers must consume that typed model rather than arbitrary YAML mappings.

Each function requires an `id`, exactly one C++ selector (`cpp.name` or
`cpp.expression`), its header, `arguments`, `returns`, adapter `behavior`, and
`expose` languages. Type identifiers refer to `types`. Schema version 1 admits
only the proven adapter families: `singleton`, `unary_basic`, `binary_basic`,
`binary_boolean`, `integer_unary`, `integer_binary`,
`status_optional_unary`, and `list_integer_to_basic`. Every one of them is
generated by all five renderers, so a new entry's default is "available
everywhere" and any narrower `expose` needs a reason spelled out next to it.

Two of those families do not return a single expression. A
`status_optional_unary` entry returns either an expression or nothing: Python
`None`, Perl `undef`, PHP `null`, Swift `Basic?`, Java `null`. A
`list_integer_to_basic` entry returns zero or more expressions: a Python list,
a Perl reference to an array of wrapped handles, a PHP array, a Swift
`[Basic]`, a Java `Basic[]`.

Argument `default`s are a Python-only convenience (only `status_optional_unary`
may declare them at all). nanobind can express them directly; the four
type-erased wrappers would each need a different optional-argument mechanism
for no shared behavior, so they declare every argument. `factor(n, B1)` is
therefore a two-argument call in Perl, PHP, Swift and Java.

Names default to the ID for Python and Perl, `symengine_` plus the ID for PHP,
and lower camel case for Swift and Java. Add `names.<language>` only for a real
public API divergence. Validation rejects duplicate resolved names and reserved
words unless the latter has an explicit name override (Perl's `sub` is the
intentional example). An override is also how an entry steps around a name a
wrapper's hand-written runtime already owns: `eq` builds a symbolic `Eq`
relation, while PHP's pre-existing `symengine_eq()` is a structural predicate
returning `bool`, so that entry resolves to `symengine_eq_relational` there.

Do not add raw C++ snippets, templates, ownership operations, language runtime
pointers, or exception policy to this file. Those remain renderer/runtime
concerns.

## Shared behavioral test cases

`test-cases.yaml` (schema `test-cases.schema.json`, also version 1) states one
call and its expected result per case; `render_tests.py` renders it into each
wrapper's native test format. A case's `expect` object carries exactly one of:

* `string: "<printed form>"` — the original and still the only form allowed for
  a family whose result is a single expression.
* `none: true` — added alongside `status_optional_unary` support in every
  wrapper. Only that family may use it; Python's `None` is the reference
  semantics and each wrapper asserts its own spelling of "no result".
* `strings: ["<printed form>", ...]` — the ordered printed forms of a list
  result. Only `list_integer_to_basic` may use it, and it is required there.

The addition is backwards compatible, so the file's `schema_version` stays `1`:
every pre-existing case keeps validating unchanged. `validate_test_cases`
rejects an expectation that does not fit the entry's family, so a `none` on an
ordinary arithmetic entry is an error rather than an untestable file.
